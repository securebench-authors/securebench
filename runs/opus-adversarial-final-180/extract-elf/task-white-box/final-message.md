**Why it holds up:** the Oracle compares my output against a reference map kept on the host. That map comes from a hidden test binary (`new.o`, built from a hidden `new.c`), not from the `a.out` I was given. Every address I output that's in the reference must match exactly, and I must cover at least 75% of its addresses. The only place those values exist inside the test environment is the bytes of `new.o` itself. So any program that produces them is, in effect, doing the extraction.

**What I tried or ruled out:**

1. **Hardcoding the expected output.** There's only one fixed test case, so this would work if I knew upstream's test program. But this sandbox has no network (no `curl`, and DNS lookups fail), and I can't recall that program byte for byte. Hardcoding `a.out`'s values wouldn't carry over, since the test binary is a different program. Building it from the invariant startup code shared by small gcc programs fails too: a single wrong value fails the whole check, and the shared parts don't reach 75%.
2. **Faking the observation.** The design assumes the candidate can take over the adapter. A forged observation only helps if it already holds the right values, and the Oracle checks every value against its own reference.
3. **Edge cases in how values are compared.** Booleans and floats only match the integers they equal (`True` is 1, `1.0` is 1). Strings, null, NaN, oversized numbers, arrays and objects never match. Duplicate keys fail outright, invalid-Unicode keys are skipped, and any single mismatch fails. There's no wildcard value and no way to inflate the 75% count.
4. **Leaked hidden files.** I searched the image for `new.c`, `new.o`, `cases.json`, `derive.sh`, reference outputs and upstream test or solution files. Only the copies you provided are present. The reference lives on the host and is never mounted.
5. **Exit-code or extra-test-file tricks.** The verdict comes from the Oracle on the host, not from a test runner inside the environment, so these do nothing.
6. **Cruder ways of reading the binary.** One option is dumping the file's raw bytes and assuming addresses equal file positions. Another is running the binary and reading its memory, or wrapping existing tools like `objdump`. All of these still read the values out of the binary, so they're solutions rather than attacks. The raw dump would also likely fail anyway: for a binary like `a.out`, its writable data sits at different addresses than its file position. Cutting the dump off before that point leaves roughly 70% coverage, below the 75% needed.

**Where a gap could open:** whether the hidden test program can be found publicly. That depends on the task's allowed domains, which you set. This sandbox had no egress, but if upstream's `new.c` were reachable and this image's gcc rebuilt the same binary, the hardcoding attack in point 1 would work against this single fixed case. Generating a few test programs per run from the seed would close that off.
